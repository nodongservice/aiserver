# 접근성 점수 계산 정책 가이드

## 1. 목적

이 문서는 BridgeWork FastAPI AI/GIS Service의 접근성 점수 계산 기준을 정의한다.

접근성 점수는 사용자의 장애 유형, 필요 지원 조건, 이동 선호, 업무환경 선호/기피 조건, 공공데이터/GIS 근거를 바탕으로 계산한다.

최종 점수는 룰 기반으로 계산한다.

LLM은 점수를 직접 계산하거나 변경하면 안 된다.  
LLM은 이미 계산된 점수, 긍정 요인, 위험 요인, 근거 데이터를 바탕으로 사용자 친화적 설명만 생성한다.

---

## 2. 기본 원칙

### 2.1 점수는 룰 기반이다

FastAPI는 정해진 scoring rule에 따라 점수를 계산한다.

점수 계산에 사용하는 주요 데이터는 다음과 같다.

- 사용자 장애 유형
- 사용자 필요 지원 조건
- 사용자 업무환경 선호/기피 조건
- 사용자 이동수단 선호
- 공고의 업무환경 태그
- 공고의 지원 태그
- 표준사업장 여부
- 장애인 우대/전형 여부
- 근무지 주변 버스정류장
- 근무지 주변 횡단보도
- 근무지 주변 신호등
- 음향신호기
- 보도턱낮춤
- 점자블록
- 지하철 출입구 리프트
- 휠체어 리프트
- 장애인 화장실 정보
- 계단 없는 접근 정보

### 2.2 데이터가 부족하면 단정하지 않는다

공공데이터에 정보가 없다고 해서 “접근 불가”로 단정하지 않는다.

데이터가 부족한 경우에는 다음 방식으로 처리한다.

- 점수는 과도하게 높이지 않는다.
- risk_factors에 “확인 필요” 문구를 추가한다.
- summary에 “일부 접근성 정보는 확인이 필요합니다.”를 반영할 수 있다.
- evidence_items에는 확인 가능한 근거만 담는다.

### 2.3 positive_factors와 risk_factors는 항상 함께 반환한다

추천 결과에는 긍정 요인과 위험 요인을 함께 제공한다.

사용자에게 좋은 점만 보여주면 안 된다.  
특히 접근성 정보는 사용자의 실제 이동 가능성과 업무 적합성에 영향을 줄 수 있으므로 위험 요인을 숨기지 않는다.

### 2.4 장애 유형별 중요도는 다르게 본다

같은 시설이라도 장애 유형에 따라 중요도가 다르다.

예:

- 휠체어 사용자에게는 엘리베이터, 리프트, 보도턱낮춤, 계단 없는 접근이 중요하다.
- 시각장애 사용자에게는 음향신호기, 점자블록, 보행자작동신호기가 중요하다.
- 청각장애 사용자에게는 전화 업무 회피, 문자/필담 지원, 면접 편의 제공이 중요하다.
- 지체장애 사용자에게는 장시간 서기, 무거운 물건 들기, 긴 이동 동선이 위험 요인이 될 수 있다.

## 3. 총점 구조

최종 접근성 점수는 0~100점 범위를 사용한다.

권장 점수 항목은 다음과 같다.

| 항목 | 최대 점수 | 설명 |
|---|---:|---|
| transport_score | 20 | 대중교통 접근성 |
| station_access_score | 20 | 지하철/역사/리프트 접근성 |
| crosswalk_score | 20 | 횡단보도/보행 안전 접근성 |
| facility_score | 20 | 사업장/편의시설 접근성 |
| work_environment_score | 20 | 업무환경 적합성 |
| risk_penalty | 음수 | 위험 요소 감점 |

총점 계산:

`total = transport_score + station_access_score + crosswalk_score + facility_score + work_environment_score + risk_penalty`

최종 점수는 0~100 범위로 보정한다.

## 4. 등급 기준

| 등급 | 점수 기준 | 의미 |
|---|---:|---|
| GOOD | 80점 이상 | 접근성 조건이 비교적 양호한 공고 |
| CAUTION | 60점 이상 80점 미만 | 일부 확인이 필요하지만 검토 가능한 공고 |
| RISK | 60점 미만 | 사용자 조건과 충돌하거나 접근성 정보가 부족한 공고 |

주의:

- GOOD이어도 risk_factors가 있을 수 있다.
- RISK라고 해서 지원 불가를 의미하지 않는다.
- RISK는 “지원 전 확인 필요성이 높음”을 의미한다.

## 5. 장애 유형 태그 기준

현재 MVP에서 사용하는 장애 유형 태그는 다음과 같다.

| 태그 | 의미 |
|---|---|
| wheelchair | 휠체어 이용자 |
| mobility | 지체/이동약자 |
| blind | 전맹 |
| low_vision | 저시력 |
| hearing | 청각장애 |
| unknown | 분류 불명 또는 기타 |

프론트/Spring에서 한글 선택값을 넘기면 FastAPI의 `/api/v1/tags/normalize`가 위 표준 태그로 변환한다.

## 6. 대중교통 접근성 점수

항목명:

`transport_score`

최대 점수:

`20점`

### 6.1 기본 기준

| 조건 | 점수 |
|---|---:|
| 반경 500m 이내 버스정류장 2개 이상 | +10 |
| 반경 500m 이내 버스정류장 1개 | +6 |
| 가장 가까운 버스정류장 300m 이내 | +5 |
| 가장 가까운 버스정류장 500m 이내 | +3 |
| 버스정류장 정보 없음 | +0 |

### 6.2 장애 유형별 보정

| 조건 | 점수 |
|---|---:|
| 휠체어 사용자 + low_floor_bus 필요 + 버스정류장 있음 | +3 |
| 이동약자 + 버스정류장 300m 이내 | +2 |
| 버스 선호 사용자 + 버스정류장 있음 | +2 |

### 6.3 확인 필요 조건

다음 상황에서는 risk_factors에 확인 필요 문구를 추가한다.

- 사용자가 low_floor_bus를 필요로 하지만 저상버스 정류장 여부를 확인할 수 없는 경우
- 버스정류장은 있으나 저상버스 대응 여부 데이터가 없는 경우
- 대중교통 정보가 전혀 없는 경우

## 7. 지하철/역사 접근성 점수

항목명:

`station_access_score`

최대 점수:

`20점`

### 7.1 기본 기준

| 조건 | 점수 |
|---|---:|
| 근처 지하철 출입구 엘리베이터 정보 있음 | +8 |
| 근처 휠체어 리프트 정보 있음 | +6 |
| 지하철 접근성 시설이 300m 이내 | +4 |
| 지하철 접근성 시설이 500m 이내 | +2 |

### 7.2 휠체어 사용자 보정

| 조건 | 점수 |
|---|---:|
| 휠체어 사용자 + 엘리베이터 있음 | +4 |
| 휠체어 사용자 + 휠체어 리프트 있음 | +3 |
| 휠체어 사용자 + 엘리베이터/리프트 모두 없음 | risk_factors 추가 |

### 7.3 확인 필요 조건

다음 상황에서는 risk_factors에 확인 필요 문구를 추가한다.

- 휠체어 사용자에게 필요한 엘리베이터/리프트 정보가 없는 경우
- 지하철 접근성 시설 데이터가 부족한 경우
- 역명 또는 출입구 좌표 매핑 신뢰도가 낮은 경우

## 8. 횡단보도/보행 안전 점수

항목명:

`crosswalk_score`

최대 점수:

`20점`

| 조건 | 점수 |
|---|---:|
| 반경 500m 이내 횡단보도 2개 이상 | +6 |
| 반경 500m 이내 횡단보도 1개 | +3 |

| blind/low_vision + 점자블록 정보 없음 | risk_factors 추가 |

### 8.4 확인 필요 조건

- 주변 횡단보도는 있으나 보행 안전 속성 정보가 없는 경우
- 음향신호기/점자블록/보도턱낮춤 여부가 확인되지 않는 경우
- 근무지 주변 보행 안전시설 정보가 부족한 경우

## 9. 사업장/편의시설 접근성 점수

항목명:

`facility_score`

최대 점수:

`20점`

### 9.1 기본 기준

| 조건 | 점수 |
|---|---:|
| 장애인 표준사업장으로 확인됨 | +8 |
| 장애인 우대/전형 공고로 확인됨 | +5 |
| 장애인 화장실 정보 있음 | +4 |
| 계단 없는 접근 정보 있음 | +3 |

### 9.2 휠체어 사용자 보정

| 조건 | 점수 |
|---|---:|
| 휠체어 사용자 + 장애인 화장실 있음 | +3 |
| 휠체어 사용자 + 계단 없는 접근 있음 | +3 |
| 휠체어 사용자 + 장애인 화장실 정보 없음 | risk_factors 추가 |
| 휠체어 사용자 + 계단 없는 접근 정보 없음 | risk_factors 추가 |

### 9.3 확인 필요 조건

다음 상황에서는 risk_factors에 확인 필요 문구를 추가한다.

- 장애인 화장실 여부가 확인되지 않는 경우
- 건물 출입구의 계단 없는 접근 가능 여부가 확인되지 않는 경우
- 표준사업장 여부가 확인되지 않는 경우
- 장애인 우대/전형 여부가 확인되지 않는 경우

항목명:

`work_environment_score`

최대 점수:

`20점`

### 10.1 기본 가점

| 조건 | 점수 |
|---|---:|
| 컴퓨터 기반 업무 | +4 |
| 문서 작업 중심 업무 | +4 |
| 조용한 근무환경 | +3 |
| 필담/문자 기반 커뮤니케이션 지원 | +3 |
| 면접 편의 제공 가능성 | +3 |
| 장애인 친화 공고 | +3 |

### 10.2 업무환경 충돌 감점

| 사용자 선호/기피 | 공고 태그 | 감점 |
|---|---|---:|
| avoid_phone_work | phone_work | -5 |
| avoid_long_standing | long_standing_or_walking | -6 |
| avoid_heavy_lifting | heavy_lifting | -6 |
| avoid_noise | noisy_environment | -4 |
| avoid_night_shift | night_shift | -4 |

### 10.3 청각장애 사용자 보정

| 조건 | 점수 |
|---|---:|
| hearing + chat_communication 있음 | +4 |
| hearing + avoid_phone_work + phone_work 있음 | risk_factors 추가 |
| hearing + 전화 응대 중심 업무 | 감점 강화 |

### 10.4 이동약자/지체장애 사용자 보정

| 조건 | 점수 |
|---|---:|

| mobility/wheelchair + 무거운 물건 취급 태그 있음 | risk_factors 추가 |
| mobility/wheelchair + 컴퓨터/문서 업무 중심 | 가점 |

## 11. 위험 요소 감점

항목명:

`risk_penalty`

risk_penalty는 음수 값으로 계산한다.

### 11.1 기본 감점

| 조건 | 감점 |
|---|---:|
| 필수 접근성 정보 다수 누락 | -5 |
| 사용자 기피 업무환경과 충돌 1개 | -5 |
| 사용자 기피 업무환경과 충돌 2개 이상 | -10 |
| 휠체어 사용자에게 엘리베이터/리프트 정보 없음 | -5 |
| 장애인 화장실/계단 없는 접근 정보 모두 없음 | -5 |
| 공고 위치 좌표 없음 | -10 |
| GIS 근거 데이터 없음 | -5 |

### 11.2 감점 원칙

- 데이터 없음과 실제 불가능을 구분한다.
- 데이터 없음은 “확인 필요”로 표현한다.
- 사용자의 필수 지원 조건과 명확히 충돌할 때만 큰 감점을 준다.
- 중복 감점으로 점수가 과도하게 낮아지지 않도록 상한을 둔다.

권장 risk_penalty 하한:

`-20`

## 12. 데이터 부족 정책

데이터 부족은 다음 세 단계로 구분한다.

### 12.1 정보 없음

예:

- 장애인 화장실 여부 데이터 없음
- 계단 없는 접근 여부 데이터 없음
- 저상버스 정류장 여부 데이터 없음

처리:

- risk_factors에 확인 필요 문구 추가
- 직접적인 불가능으로 표현하지 않음
- 점수는 보수적으로 계산

### 12.2 정보 일부 있음

예:

- 버스정류장 위치는 있으나 저상버스 여부 없음
- 횡단보도는 있으나 보도턱낮춤 정보 없음
- 역명은 있으나 출입구 좌표 없음

처리:

- 확인 가능한 부분만 positive_factors에 반영
- 부족한 부분은 risk_factors에 반영

### 12.3 정보 충돌

예:

- 사용자가 전화 업무를 피하고 싶은데 공고 태그에 phone_work가 있음
- 사용자가 장시간 서기 어려운데 long_standing_or_walking 태그가 있음
- 휠체어 사용자에게 접근성 시설 근거가 전혀 없음

처리:

- risk_factors에 명확히 표시
- risk_penalty 적용
- 등급이 GOOD이어도 summary에 확인 필요 반영

## 13. 장애 유형별 핵심 확인 항목

### 13.1 휠체어 사용자

핵심 확인 항목:

- 계단 없는 접근
- 엘리베이터
- 휠체어 리프트
- 보도턱낮춤
- 장애인 화장실
- 저상버스 접근성
- 장시간 서기/이동 업무 여부
- 무거운 물건 취급 여부

긍정 요인 예시:

- 근처 지하철역 또는 출입구에 엘리베이터 정보가 있습니다.
- 근처 이동 구간에 휠체어 리프트 정보가 있습니다.
- 근무지 주변 횡단보도에 보도턱낮춤 정보가 확인됩니다.
- 장애인 표준사업장으로 확인됩니다.

위험 요인 예시:

- 근무지 출입구의 계단 없는 접근 가능 여부는 확인이 필요합니다.
- 장애인 화장실 정보는 아직 확인되지 않았습니다.
- 장시간 서거나 이동하는 업무가 포함될 수 있습니다.
- 무거운 물건을 취급하는 업무가 포함될 수 있습니다.

### 13.2 시각장애 사용자

핵심 확인 항목:

- 음향신호기
- 보행자작동신호기
- 점자블록
- 잔여시간표시기
- 복잡한 보행 동선 여부
- 화면 중심 업무 여부
- 안내/보조 지원 여부

긍정 요인 예시:

- 근무지 주변에 시각장애인용 음향신호기 정보가 확인됩니다.
- 근무지 주변 보행 구간에 점자블록 정보가 확인됩니다.
- 근무지 주변에 보행자작동신호기 정보가 확인됩니다.

위험 요인 예시:

- 근무지 주변 음향신호기 여부 확인이 필요합니다.
- 근무지 주변 점자블록 여부 확인이 필요합니다.
- 시각 보조 지원 여부는 확인이 필요합니다.

### 13.3 청각장애 사용자

핵심 확인 항목:

- 전화 응대 업무 여부
- 듣고 말하기 중심 업무 여부
- 필담/문자 기반 커뮤니케이션 지원
- 면접 편의 제공
- 채팅 기반 소통 가능성

긍정 요인 예시:

- 필담/문자 기반 커뮤니케이션 지원 가능성이 있습니다.
- 면접 편의 제공 지원 가능성이 있습니다.
- 전화 응대가 적은 업무환경으로 분류됩니다.

위험 요인 예시:

- 전화 응대 업무가 포함되어 사용자 선호와 충돌할 수 있습니다.
- 듣고 말하기 중심 업무가 포함될 수 있어 확인이 필요합니다.

### 13.4 이동약자/지체장애 사용자

핵심 확인 항목:

- 장시간 서기/걷기 여부
- 무거운 물건 취급 여부
- 계단 없는 접근
- 가까운 대중교통
- 엘리베이터/리프트
- 화장실 접근성

긍정 요인 예시:

- 컴퓨터 사용 중심 업무로 분류됩니다.
- 문서 작업 중심 업무로 분류됩니다.
- 근무지 주변 대중교통 정보가 확인됩니다.

위험 요인 예시:

- 장시간 서거나 이동하는 업무가 포함될 수 있습니다.
- 무거운 물건을 취급하는 업무가 포함될 수 있습니다.

## 14. evidence_items 사용 원칙

evidence_items는 점수 계산에 사용한 근거 데이터를 담는다.

각 evidence item은 다음 정보를 포함한다.

- source_type
- source_name
- description
- distance_meters
- record_id

### 14.1 record_id 기준

record_id는 기본적으로 Spring의 `public_data_record.id`를 사용한다.

이 값은 사용자가 “왜 이 점수인가요?”라고 물었을 때 원본 공공데이터를 추적하기 위한 기준이다.

### 14.2 evidence 생성 기준

다음 데이터는 evidence_items로 남긴다.

- 근처 버스정류장
- 근처 횡단보도
- 근처 신호등
- 음향신호기
- 지하철 출입구 리프트
- 휠체어 리프트
- 표준사업장 근거
- 장애인 우대/전형 근거
- 교통약자 이동지원센터

### 14.3 evidence 개수 제한

한 공고당 evidence_items가 너무 많아지면 응답이 커진다.

권장 제한:

- source_type별 대표 1~3개
- 전체 evidence_items 10개 이하

## 15. LLM 사용 원칙

LLM은 점수 계산에 개입하지 않는다.

LLM 입력으로 사용할 수 있는 값:

- accessibility_score
- accessibility_grade
- score_detail
- positive_factors
- risk_factors
- evidence_items
- summary

LLM이 하면 안 되는 것:

- 점수 재계산
- 등급 변경
- 위험 요인 삭제
- 데이터 부족을 확정 표현으로 바꾸기
- 근거 없는 긍정 표현 추가

LLM 설명에서 반드시 유지해야 하는 표현 원칙:

- 데이터 부족은 “확인 필요”
- 위험 요인은 숨기지 않음
- 사용자의 장애 유형을 낙인찍는 표현 금지
- 지원 불가/불가능 같은 단정 표현 금지
- “지원 전 확인을 권장합니다” 형태의 안전한 표현 사용

## 16. 향후 개선 항목

### 16.1 scoring_version

Phase 11에서는 scoring_version을 스킵했지만, 운영 단계에서는 추가를 권장한다.

예:

`v1-rule-gis-basic`

사용 목적:

- 분석 결과 캐싱
- 점수 정책 변경 추적
- 과거 분석 결과와 신규 분석 결과 구분

### 16.2 feature importance 설명

향후 사용자가 “왜 이 공고가 추천됐나요?”라고 물었을 때 항목별 기여도를 설명할 수 있다.

예:

- 대중교통 접근성 +15
- 보행 안전 +12
- 업무환경 적합성 +18
- 위험 감점 -5

### 16.3 실제 경로 기반 분석

현재는 반경 기반 근접 검색이다.

향후에는 다음을 고려할 수 있다.

- 실제 보행 경로 거리
- 환승 횟수
- 지하철 출입구별 엘리베이터 위치
- 도로 경사도
- 보행 네트워크 단절 여부
- 실시간 시설 고장 정보
