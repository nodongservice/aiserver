# BridgeWork Product Policy Agent

## 1. 문서 목적

이 문서는 BridgeWork 프로젝트의 핵심 사용자, 주요 기능, AI 사용 범위, 접근성 설계 원칙, 추천/설명 정책을 정리한 에이전트용 기준 문서이다.

BridgeWork 관련 코드를 작성하거나 기능을 제안하는 에이전트는 이 문서를 기준으로 다음 사항을 지켜야 한다.

- 장애인 구직자의 실제 취업 가능성과 이동 가능성을 우선한다.
- 접근성 데이터를 과신하지 않는다.
- 데이터가 부족한 경우 “불가능” 또는 “위험”으로 단정하지 않고 “확인 필요”로 표현한다.
- AI는 점수를 임의로 계산하지 않고, 정해진 룰 기반 결과를 설명하는 역할을 우선한다.
- 기능 구현 시 WCAG 2.2 AA 수준의 접근성을 고려한다.

---

## 2. 서비스 개요

BridgeWork는 장애인 구직자를 위한 접근성 기반 일자리 추천 서비스이다.

단순히 구인 공고를 나열하는 것이 아니라, 사용자의 장애 유형, 필요한 지원, 선호 업무환경, 거주 지역, 통근 가능 범위, 공공 접근성 데이터를 함께 고려하여 현실적으로 지원 가능한 공고를 추천한다.

핵심 방향은 다음과 같다.

- 구직자에게 “나에게 맞는 일자리”를 추천한다.
- 공고별 직무 적합도와 접근성 적합도를 함께 보여준다.
- 지도 기반으로 출근 가능성과 주변 접근성 정보를 시각화한다.
- 데이터가 부족한 항목은 명확하게 “확인 필요”로 안내한다.
- AI 설명은 사용자가 이해하기 쉬운 요약, 긍정 요인, 위험 요인, 확인 사항 중심으로 제공한다.

## 3. 메인 타깃

### 3.1 1차 타깃: 핵심 사용자

구직 중인 장애인, 특히 다음 사용자를 핵심 타깃으로 한다.

- 중증장애인
- 이동약자
- 지역 기반 취업 희망자
- 직장 접근성을 중요하게 고려해야 하는 구직자

현재 화면 구성에서 고려하는 장애 유형은 다음과 같다.

- 지체장애: 휠체어 사용자
- 시각장애: 전맹, 부분맹, 저시력 사용자
- 청각장애: 청각장애, 농난청 사용자

장애 유형별로 사용 흐름 자체가 접근성 있게 설계되어야 한다.

### 3.2 1.5차 타깃

직장 접근성을 중요하게 여기는 구직 청년을 확장 타깃으로 본다.

예를 들어 다음과 같은 사용자가 포함될 수 있다.

- 통근 시간이 중요한 사용자
- 조용한 근무환경을 선호하는 사용자
- 재택근무, 유연근무, 단축근무를 선호하는 사용자
- 업무환경 리스크를 사전에 알고 싶은 사용자

### 3.3 2차 타깃: 활용 기관

다음 기관이 지역 내 장애인 친화 일자리 지도와 추천 결과를 상담 도구로 활용할 수 있다.

- 고용복지플러스센터
- 장애인고용공단 지사
- 지자체 취업지원기관
- 장애인 취업 지원 기관

### 3.4 3차 타깃: 구인 기업

장애인 채용을 희망하는 사업장도 확장 타깃이다.

기업은 향후 다음 목적에 BridgeWork를 활용할 수 있다.

- 자사 공고에 적합한 구직자군 파악
- 장애인 채용 친화 요소 점검
- 지원 전 확인이 필요한 접근성 항목 파악
- 표준사업장, 장애인 전형, 면접 편의 제공 여부 안내

## 4. AI 사용 범위

BridgeWork에서 AI는 다음 기능에 사용한다.

### 4.1 사용자 조건 태그화

사용자가 온보딩 또는 필터에서 입력한 내용을 내부 표준 태그로 변환한다.

예시:

- “휠체어 이용” → `wheelchair`
- “전화 업무가 적었으면 좋겠음” → `avoid_phone_work`
- “조용한 곳 선호” → `prefer_quiet_environment`
- “문자 소통 가능” → `chat_communication`
- “계단 없는 출입 필요” → `step_free_access`

### 4.2 접근성 추천 결과 설명

AI는 공고 추천 결과와 접근성 분석 결과를 사용자가 이해하기 쉬운 문장으로 설명한다.

설명에는 다음 요소를 포함한다.

- 짧은 요약
- 긍정 요인
- 위험 요인
- 확인 필요 사항
- 근거 데이터
- 지원 전 체크포인트

### 4.3 경로 추천 결과 설명

향후 장애 유형별 접근 경로 추천 기능이 추가될 경우, AI는 경로 결과를 설명하는 데 사용한다.

예시:

- “엘리베이터가 있는 지하철 출입구를 기준으로 접근 가능한 경로입니다.”
- “횡단보도 보도턱 낮춤 정보가 확인되지 않아 지원 전 확인이 필요합니다.”
- “시각장애 사용자의 경우 음향신호기 또는 점자블록 여부 확인이 필요합니다.”

### 4.4 AI가 하지 말아야 할 일

AI는 다음을 해서는 안 된다.

- 데이터가 부족한데 접근 가능/불가능을 단정하지 않는다.
- 장애 유형만으로 사용자의 능력이나 업무 가능 여부를 단정하지 않는다.
- 점수를 임의로 생성하지 않는다.
- 공공데이터에 없는 정보를 있는 것처럼 말하지 않는다.
- 위험 요인을 과장하지 않는다.
- 사용자가 지원하지 못할 것처럼 단정적인 표현을 쓰지 않는다.
- “장애인이므로 부적합”과 같은 차별적 판단을 하지 않는다.

## 5. 주요 기능

## 기능 0. 프로필 생성, 온보딩, 로그인/회원가입

### 5.1 회원가입 및 로그인

지원 예정 로그인 방식은 다음과 같다.

- 카카오 연동 회원가입 및 로그인
- 네이버 연동 회원가입 및 로그인

본인인증 기능은 현재 도입하지 않는 것으로 결정한다.

### 5.2 추가 정보 입력

회원가입 이후 추천 품질을 위해 추가 정보를 입력받는다.

필수 또는 주요 입력 정보는 다음과 같다.

- 이름
- 나이
- 성별
- 위치정보
- 전화번호

위치정보는 상세 주소가 아니라 동 단위까지 입력하는 방향을 우선한다.

예시:

- 서울특별시 마포구 공덕동
- 경기도 수원시 영통구 원천동

정확한 주소를 요구하지 않는 이유는 다음과 같다.

- 개인정보 부담을 줄이기 위해
- 초기 추천에는 생활권 단위 정보가 충분히 유용하기 때문에
- 사용자의 접근성 부담을 낮추기 위해

## 기능 1. 직장 필터 생성

사용자는 자신에게 맞는 직장 필터를 만들 수 있다.

필터는 최대 3개까지 저장하는 방향을 우선 고려한다.
최대 개수는 추후 논의에 따라 변경될 수 있다.

### 6.1 필수 입력 항목

필수 입력 항목은 기본적인 일자리 추천에 필요한 정보로 구성한다.

- 희망 직무
- 희망 근무지역
- 통근 범위
- 고용형태
- 경력
- 학력

통근 범위 예시는 다음과 같다.

- 30분 미만
- 30분 ~ 1시간
- 1시간 ~ 1시간 30분
- 1시간 30분 ~ 2시간
- 2시간 이상

필수 입력 항목은 일반 구직 플랫폼에서 사용하는 기본 공고 필터와 유사하게 구성한다.

### 6.2 선택 입력 항목

장애 유형, 필요한 지원, 선호/기피 업무환경 등은 민감 정보가 될 수 있으므로 선택 입력으로 둔다.

화면에는 다음과 같은 안내 문구를 제공하는 것을 권장한다.

“더 정확한 접근성 추천을 위해 장애 유형과 필요한 지원을 선택할 수 있어요.”

“입력하지 않아도 기본 일자리 추천은 이용할 수 있어요.”

선택 입력 항목은 다음과 같다.

### 선호/기피 산업

- 선호 산업 최대 3개
- 기피 산업 최대 3개

선호 산업은 정렬 우선순위에 반영하고, 기피 산업은 정렬 후순위에 반영한다.

### 장애의 종류

- 지체장애: 휠체어
- 시각장애: 저시력, 전맹
- 청각장애: 농난청

### 필요 지원

- 장애인 표준사업장 해당 여부
- 장애인 전형/우대 공고
- 재택근무 가능
- 유연근무/단축근무 가능
- 근로지원인 연계 가능
- 보조공학기기 지원 가능
- 수어 통역 필요
- 필담/문자 커뮤니케이션 필요
- 전화 응대 적은 업무 선호
- 면접 편의 제공 필요
- 계단 없는 출입 필요
- 조용한 근무환경 선호

### 기타 선택 항목

- 자격증
- 복리후생
- 우대 전공

### 6.3 AI 태그 구조화

사용자 입력은 AI 또는 룰 기반 로직을 통해 다음 구조로 변환한다.

- 직무 태그
- 환경 제약 태그
- 필요 지원 태그
- 선호 업무환경 태그
- 기피 업무환경 태그
- 장애 유형 태그
- 통근 조건 태그

FastAPI에서는 이 태그를 기반으로 접근성 분석 및 설명 생성을 수행한다.

## 기능 1-2. BridgeWork 양식 포트폴리오 생성

추가 개발 기능으로, 사용자가 기존 타 플랫폼 이력서 또는 포트폴리오를 업로드하면 AI가 BridgeWork 양식에 맞는 포트폴리오를 생성한다.

예상 기능은 다음과 같다.

- 이력서/포트폴리오 파일 업로드
- OCR 기반 텍스트 추출
- 직무 경험 요약
- 보유 역량 구조화
- 희망 직무와의 연결
- BridgeWork 추천 시스템에 활용 가능한 태그 추출

이 기능은 핵심 MVP 이후 추가 개발 범위로 둔다.

## 기능 2. 맞춤 일자리 추천

사용자 화면에서는 “나에게 맞는 일자리” 정도의 표현을 우선 고려한다.

기능 2는 실시간 구인 현황, 구직자 프로필, 직장 필터를 바탕으로 추천 공고 목록을 제공한다.

추천 공고는 점수가 높은 순으로 정렬한다.

### 7.1 추천 점수 항목

추천 점수는 다음 항목을 조합하여 계산한다.

| 점수 항목 | 의미 | 예시 |
|---|---|---|
| 직무 적합도 | 희망 직무, 경력, 학력, 자격증과 공고의 일치도 | 사무보조 희망, 컴퓨터 활용 가능 |
| 근무조건 적합도 | 고용형태, 근무시간, 재택/하이브리드/탄력근무 여부 | 단축근무 가능, 정규직 선호 |
| 장애 지원 적합도 | 사용자가 필요한 지원을 회사가 제공하는지 | 근로지원인, 보조공학기기, 수어통역, 면접 편의 |
| 업무환경 적합도 | 장애 특성과 업무 부담 요소가 충돌하지 않는지 | 전화응대, 장시간 서기, 소음, 야간근무 |
| 기업 안정성/채용 친화도 | 장애인 고용 경험, 표준사업장, 기업 규모 등 | 장애인 전형, 장애인 우대, 표준사업장 |
| 접근성 요약 점수 | 지역 접근성/사업장 접근성 일부 반영 | 통근 가능, 건물 접근 가능 |

### 7.2 예시 점수 구성

예시:

최종 적합도 84점

- 직무 적합도: 28/30
  - 희망 직무인 사무보조와 일치
  - 컴퓨터 활용 능력 우대 조건과 일치

- 근무조건 적합도: 17/20
  - 단축근무 가능
  - 야간근무 없음

- 장애 지원 적합도: 15/20
  - 장애인 전형 있음
  - 면접 편의 제공 가능
  - 문자 기반 커뮤니케이션 가능

- 업무환경 적합도: 14/15
  - 컴퓨터 사용 중심
  - 장시간 서서 근무 없음
  - 무거운 물건 취급 없음

- 기업/채용 안정성: 6/10
  - 장애인 우대 공고
  - 표준사업장 여부는 확인 필요

- 접근성 요약: 4/5
  - 통근 및 건물 접근성 양호

### 7.3 추천 시 고려할 장애 지원 요소

다음 요소는 장애인 구직자가 취업 시 중요하게 고려할 수 있는 항목이다.

- 재택근무 가능
- 하이브리드 근무 가능
- 탄력근무 가능
- 단축근무 가능
- 근로지원인 연계 가능
- 보조공학기기 지원 가능
- 수어 통역 지원 가능
- 문자/채팅 기반 커뮤니케이션 가능
- 면접 시 편의 제공 가능
- 장애인 전형 여부
- 장애인 우대 여부

### 7.4 추천 시 고려할 업무환경 요소

다음 업무환경 요소를 태그로 관리한다.

- 사무직 중심
- 현장직 포함
- 고객응대 있음
- 전화응대 있음
- 장시간 서서 근무
- 반복 작업
- 소음 많은 환경
- 야외 근무
- 야간 근무
- 교대 근무
- 무거운 물건 취급
- 빠른 이동 필요
- 세밀한 손작업 필요
- 컴퓨터 사용 중심
- 대면 커뮤니케이션 많음
- 문서 작업 많음

업무환경 요소는 단순히 감점 요소가 아니라, 사용자의 선호/기피 조건과 비교하여 판단한다.

예를 들어 전화응대가 있는 공고라도 모든 사용자에게 위험 요인은 아니다.
다만 사용자가 `avoid_phone_work`를 선택한 경우에는 확인 필요 또는 위험 요인으로 표시할 수 있다.

## 기능 3. 지역 접근성 지도

기능 3은 BridgeWork의 1순위 핵심 기능이다.

지역을 기준으로 구직자 생활권 내 접근 가능한 사업장을 지도에 시각화한다.

### 8.1 목적

지역 접근성 지도는 다음 목적을 가진다.

- 구직자에게 현실적인 출근 가능 공고를 직관적으로 보여준다.
- 공고 위치 주변의 접근성 정보를 함께 제공한다.
- 휠체어, 시각, 청각 사용자에게 필요한 접근성 확인 항목을 안내한다.
- 추천 공고의 접근성 점수와 근거를 지도에서 확인할 수 있게 한다.

### 8.2 MVP 사용 예정 데이터

MVP에서 우선 고려하는 데이터는 README.md의 동기화 대상 데이터에 포함된 항목만 사용한다.

- 사용자 위치 동 단위
- 공고 근무지 위치
- `KEPAD_RECRUITMENT`: 공고 기본 정보, 사업장명, 사업장주소, 직무, 고용형태, 임금, 업무환경 항목
- `KEPAD_STANDARD_WORKPLACE`: 장애인 표준사업장 여부
- `KEPAD_SUPPORT_AGENCY`: 근로지원인 수행기관 정보
- `NATIONWIDE_BUS_STOP`: 근무지 주변 버스정류장 위치 및 거리
- `NATIONWIDE_CROSSWALK`: 근무지 주변 횡단보도 위치 및 보행 안전 속성
  - 보행자신호등 여부
  - 보행자작동신호기 여부
  - 음향신호기 여부
  - 보도턱낮춤 여부
  - 점자블록 여부
- `NATIONWIDE_TRAFFIC_LIGHT`: 근무지 주변 신호등, 보행자작동신호기, 시각장애인용 음향신호기, 잔여시간표시기 여부
- `SEOUL_SUBWAY_ENTRANCE_LIFT`: 서울시 지하철 출입구 리프트 위치정보
- `SEOUL_WHEELCHAIR_LIFT`: 서울교통공사 휠체어리프트 설치현황
- `SEOUL_TRANSPORT_WEAK_WHEELCHAIR_LIFT`: 서울교통공사 교통약자 이용정보 중 휠체어리프트 정보
- `RAIL_WHEELCHAIR_LIFT`: 국가철도공단 역사별 휠체어리프트 위치
- `RAIL_WHEELCHAIR_LIFT_MOVEMENT`: 역사별 휠체어리프트 이동동선
- `KORAIL_WEEK_PERSON_FACILITIES`: 한국철도공사 교통약자 편의시설 정보
- `TRANSPORT_SUPPORT_CENTER`: 전국교통약자이동지원센터 정보
- `VOCATIONAL_TRAINING`: 직업훈련 과정 추천
- `JOBSEEKER_COMPETENCY_PROGRAM`: 구직자 취업역량 강화 프로그램 추천
- 버스/지하철 선호도, 환승/직행 선호도는 사용자 입력값으로만 활용한다.

주의: README.md 동기화 대상에 별도 저상버스 운행 데이터는 포함되어 있지 않다. 따라서 MVP에서는 저상버스 여부를 확정 판단하지 않고, 필요 시 “확인 필요”로 안내한다.

### 8.3 2순위 데이터

다음 데이터는 MVP 이후 고도화 범위로 둔다. 단, 이 문서에서는 README.md 동기화 대상에 포함된 데이터만 언급한다.

- `SEOUL_WALKING_NETWORK` 기반 실제 보행 네트워크 분석
- `RAIL_WHEELCHAIR_LIFT_MOVEMENT` 기반 역사 내 휠체어리프트 이동동선 설명
- `TRANSPORT_SUPPORT_CENTER` 기반 교통약자 이동지원센터 안내
- `VOCATIONAL_TRAINING`, `JOBSEEKER_COMPETENCY_PROGRAM` 기반 훈련·역량 강화 프로그램 연계

경사도/고도, 실시간 환승/직행 최적화, 보행자전용도로, 주차장, 별도 장애인 편의시설 표준데이터 등 README.md 동기화 대상에 없는 데이터는 현재 기능정의서 범위에서 제외한다.

### 8.4 접근성 데이터 활용 방향

### 횡단보도 데이터

전국횡단보도표준데이터는 다음 항목을 활용할 수 있다.

- 위도/경도
- 보행자신호등 유무
- 작동신호기 유무
- 음향신호기 설치 여부
- 녹색/적색 신호시간
- 보도턱낮춤 여부
- 점자블록 유무

휠체어 경로에는 보도턱낮춤 여부가 중요하다.

시각장애 경로에는 음향신호기와 점자블록 여부가 중요하다.

### 도보 네트워크 데이터

서울시 자치구별 도보 네트워크 공간정보는 향후 경로 탐색의 뼈대 그래프로 활용할 수 있다.

노드/링크 기반 구조라 경로 탐색 알고리즘과 연결하기 좋다.

포함 가능한 보행 요소는 다음과 같다.

- 횡단보도
- 육교
- 버스정류장
- 지하철 출입구
- 보행 링크

### 신호등/음향신호기 데이터

전국신호등표준데이터는 시각장애인 이동 지원에 활용할 수 있다.

중요 항목은 다음과 같다.

- 장애인용 음향신호기 유무
- 신호등 위치
- 보행자 신호 정보

### 보행 네트워크 데이터

README.md 동기화 대상에 포함된 `SEOUL_WALKING_NETWORK`는 향후 실제 보행 네트워크 기반 길찾기 또는 보행 접근성 설명에 활용할 수 있다.

활용 가능한 항목은 다음과 같다.

- `NODE_WKT`: 보행 네트워크 노드
- `LNKG_WKT`: 보행 네트워크 링크
- `LNKG_LEN`: 링크 길이
- `CRSWK`: 횡단보도 여부
- `BRG`: 교량 여부
- `TNL`: 터널 여부
- `OVRP`: 육교 여부
- `PARK`: 공원·녹지 여부
- `BLDG`: 건물 내부 여부

전국보행자전용도로표준데이터는 README.md 동기화 대상에 없으므로 현재 문서 범위에서는 사용하지 않는다.

### 버스정류장 위치 데이터

버스정류장 좌표 데이터는 대중교통 접근성 분석에 필수이다.

현재 MVP에서는 README.md 동기화 대상인 버스정류장 위치정보를 기준으로 근무지 주변 정류장 개수와 거리를 판단한다. 저상버스 운행 여부는 별도 동기화 데이터가 없으므로 확정 판단하지 않고 “확인 필요”로 안내한다.

### 지하철 출입구, 리프트, 엘리베이터 데이터

지하철 접근성 판단에는 단순 역 위치보다 출입구 단위 정보가 중요하다.

활용 데이터 예시는 다음과 같다.

- `SEOUL_SUBWAY_ENTRANCE_LIFT`: 지하철 출입구 리프트 위치
- `SEOUL_WHEELCHAIR_LIFT`: 서울교통공사 휠체어리프트 설치현황
- `SEOUL_TRANSPORT_WEAK_WHEELCHAIR_LIFT`: 서울교통공사 교통약자 이용정보 중 휠체어리프트 정보
- `RAIL_WHEELCHAIR_LIFT`: 국가철도공단 역사별 휠체어리프트 위치
- `RAIL_WHEELCHAIR_LIFT_MOVEMENT`: 역사별 휠체어리프트 이동동선
- `KORAIL_WEEK_PERSON_FACILITIES`: 역사 편의시설, 장애인경사로, 장애인화장실, 휠체어리프트 수

어느 출입구로 들어가야 실제 접근 가능한지가 중요하다.

## 기능 3-2. 장애 유형별 접근 경로 추천

추가 개발 기능으로, 직장까지 장애 유형을 고려한 접근 경로 추천을 제공한다.

### 9.1 휠체어 사용자 경로

중요 판단 요소는 다음과 같다.

- 계단 없는 동선
- 지하철 출입구 리프트 및 역사 편의시설 정보
- 휠체어 리프트
- 보도턱 낮춤 횡단보도
- 버스정류장 접근성
- 장애인 화장실
- 경사로

### 9.2 시각장애 사용자 경로

중요 판단 요소는 다음과 같다.

- 점자블록
- 음향신호기
- 보행자 신호 정보
- 복잡한 환승 여부
- 지도 정보를 대체할 수 있는 텍스트 경로 설명
- 색상에 의존하지 않는 안내

### 9.3 청각장애 사용자 지원

중요 판단 요소는 다음과 같다.

- 문자/채팅 기반 커뮤니케이션 가능 여부
- 전화응대 업무 여부
- 수어 통역 지원 여부
- 필담 가능 여부
- 면접 편의 제공 여부
- 소리 알림에만 의존하지 않는 화면 알림

예상 항목은 다음과 같다.

- 장애인 전형 여부
- 장애인 우대 여부

- 재택근무 가능 여부
- 유연근무 가능 여부
- 면접 편의 제공 여부
- 문자/채팅 커뮤니케이션 가능 여부
- 지원 전 확인사항
- 맞춤형 면접 준비 체크리스트

이 기능은 사용자가 공고를 보고 실제 지원을 결정하기 전, 불확실성을 줄이는 데 목적이 있다.

## 11. 접근성 설계 원칙

BridgeWork는 WCAG 2.2 AA 수준의 접근성을 목표로 한다.

접근성은 단순히 화면을 보기 좋게 만드는 것이 아니라, 장애 유형과 관계없이 사용자가 회원가입, 필터 설정, 공고 탐색, 추천 결과 이해, 지원 준비를 할 수 있게 만드는 것이다.

---

## 12. 시각장애 / 저시력 사용자 접근성

### 12.1 화면 설계 원칙

- 모든 버튼, 필터, 공고 카드에 스크린리더용 라벨을 제공한다.
- 아이콘에는 대체 텍스트를 제공한다.
- 지도 마커 정보는 목록 형태로도 제공한다.
- 색상만으로 상태를 구분하지 않는다.
- 명도 대비를 충분히 확보한다.
- 큰 글씨 모드 또는 전반적으로 큰 폰트 설계를 고려한다.
- 고대비 모드를 고려한다.

### 12.2 점수 설명 원칙

“접근성 점수 82점”만 보여주지 않는다.

반드시 점수 이유를 텍스트로 함께 제공한다.

예시:

- 접근 양호: 근무지 주변에 버스정류장과 지하철역 접근성 정보가 확인됩니다.
- 주의 필요: 장애인 화장실 여부는 현재 데이터에서 확인되지 않았습니다.
- 확인 필요: 건물 내부 엘리베이터 정보는 공공데이터만으로 판단하기 어렵습니다.

### 12.3 색상 사용 원칙

초록, 노랑, 빨강만으로 상태를 표현하지 않는다.

항상 텍스트를 함께 표시한다.

예시:

- GOOD: 접근 양호
- CAUTION: 주의 필요
- RISK: 확인 필요 또는 접근성 위험 요소 있음

---

## 13. 지체장애 / 휠체어 사용자 접근성

### 13.1 웹 UI 원칙

- 가능하면 키보드만으로 회원가입, 필터 설정, 공고 탐색이 가능하도록 설계한다.
- 체크박스, 드롭다운, 지도 버튼의 클릭 영역을 크게 만든다.
- 드래그 필수 UI를 지양한다.
- 거리 반경 설정은 드래그만 제공하지 않고 버튼도 제공한다.
  - 예: 500m, 1km, 2km
- 모바일 버튼과 필터 버튼은 충분한 크기를 확보한다.

### 13.2 서비스 기능 원칙

휠체어 사용자에게 중요한 정보는 다음과 같다.

- 휠체어 출입 가능 여부
- 역사 편의시설 및 휠체어리프트 정보
- 장애인 화장실 여부
- 장애인경사로 여부
- 계단 없는 접근 가능 여부
- 지하철 출입구 리프트 위치
- 버스정류장 접근성
- 저상버스 운행 여부는 README.md 동기화 대상에 별도 데이터가 없으므로 확정 판단하지 않고 확인 필요로 안내

이 정보가 없을 경우 “불가능”으로 단정하지 않고 “확인 필요”로 안내한다.

---

## 14. 청각장애 사용자 접근성

### 14.1 화면 및 커뮤니케이션 원칙

- 고객센터/상담 문의는 전화만 제공하지 않는다.
- 채팅, 문자, 이메일 등 비음성 문의 수단을 고려한다.
- 영상/음성 안내가 있는 경우 자막을 제공한다.
- 알림은 소리만 사용하지 않고 화면 텍스트 중심으로 제공한다.

### 14.2 공고 상세 표시 항목

청각장애 사용자에게 도움이 되는 공고 정보는 다음과 같다.

- 전화응대 있음
- 대면 커뮤니케이션 많음
- 문자/채팅 기반 커뮤니케이션 가능
- 필담 가능 여부
- 수어 통역 지원 여부
- 면접 편의 제공 여부

## 15. 인지 접근성 / 쉬운 사용성

BridgeWork는 정보량이 많기 때문에 화면 복잡도를 줄이는 것도 접근성의 일부이다.

### 15.1 화면 구성 원칙

- 온보딩을 한 화면에 몰지 않고 단계별로 진행한다.
- 어려운 용어 옆에는 설명을 제공한다.
- AI 추천 결과는 긴 문장보다 요약 카드 중심으로 제공한다.
- 저장 전 확인 화면을 제공한다.
- 오류 메시지는 구체적으로 표시한다.

### 15.2 용어 설명이 필요한 예시

다음 용어는 사용자에게 설명이 필요할 수 있다.

- 근로지원인
- 보조공학기기
- 장애인 표준사업장
- 장애인 전형
- 면접 편의 제공
- 저상버스 이용 가능 여부(현재 README.md 동기화 대상에는 별도 운행 데이터가 없어 확인 필요로 안내)
- 계단 없는 출입
- 음향신호기
- 점자블록

### 15.3 오류 메시지 원칙

나쁜 예시:

- 입력 오류
- 잘못된 값입니다
- 실패했습니다

좋은 예시:

- 희망 직무를 1개 이상 선택해주세요.
- 통근 범위를 선택해주세요.
- 위치 정보는 동 단위까지 입력해주세요.
- 저장하지 않은 필터가 있습니다. 저장 후 추천을 확인할 수 있어요.

## 16. FastAPI AI/GIS 서비스 역할

BridgeWork의 현재 아키텍처에서 FastAPI는 AI/GIS 분석 서버 역할을 담당한다.

FastAPI는 프론트엔드가 직접 호출하지 않는다.

호출 흐름은 다음과 같다.

Next.js Frontend → Spring Backend → FastAPI AI/GIS Service → PostgreSQL/PostGIS

Spring Backend는 사용자, 공고, 기업, 공공데이터 동기화, 추천 결과 저장/캐싱을 담당한다.

FastAPI는 다음을 담당한다.

- 사용자 접근성 조건 태그화
- 공공데이터/GIS 기반 접근성 분석
- 공고별 접근성 점수 계산
- 긍정 요인 생성
- 위험 요인 생성
- 확인 필요 항목 생성
- 접근성 설명 생성
- 향후 LLM 기반 설명 생성

## 17. FastAPI 핵심 API

### 17.1 태그 정규화 API

POST `/api/v1/tags/normalize`

역할:

- 사용자 온보딩/직장 필터의 한글 선택값을 내부 표준 태그로 변환한다.

예시:

- 지체 - 휠체어 → `wheelchair`
- 조용한 근무환경 선호 → `prefer_quiet_environment`
- 전화 응대 적은 업무 선호 → `avoid_phone_work`

### 17.2 접근성 분석 API

POST `/api/v1/accessibility/analyze-batch`

역할:

- Spring이 넘긴 사용자 조건과 공고 후보 목록을 기반으로 접근성 점수와 설명 근거를 계산한다.

반환해야 하는 주요 항목:

- `transport_score`
- `station_access_score`
- `crosswalk_score`
- `facility_score`
- `work_environment_score`
- `risk_penalty`
- `accessibility_score`
- `accessibility_grade`
- `positive_factors`
- `risk_factors`
- `evidence_items`

등급 기준:

- GOOD: 80점 이상
- CAUTION: 60점 이상
- RISK: 60점 미만

### 17.3 접근성 설명 API

POST `/api/v1/explanations/accessibility`

역할:

- 분석 API 결과를 바탕으로 사용자용 설명을 생성한다.

현재 정책:

- 점수 계산과 설명 생성을 분리한다.
- 현재는 rule fallback 방식이다.
- `explanation_version`은 `"v1-rule-fallback"`을 사용한다.
- `used_llm`은 `false`를 반환한다.
- 향후 LLM 연결 시에도 룰 기반 fallback은 유지한다.

## 18. 점수 계산 및 설명 정책

### 18.1 점수 계산 원칙

점수는 룰 기반으로 계산한다.

LLM은 점수를 계산하지 않는다.

LLM 또는 설명 서비스는 이미 계산된 점수와 근거를 바탕으로 자연어 설명만 생성한다.

### 18.2 데이터 부족 정책

데이터가 부족한 경우 다음 원칙을 지킨다.

- 접근 불가로 단정하지 않는다.
- 위험하다고 과장하지 않는다.
- “확인 필요”로 표시한다.
- 어떤 데이터가 부족한지 구체적으로 설명한다.
- 사용자가 지원 전 확인할 수 있는 체크포인트를 제공한다.

예시 문구:

- 장애인 화장실 정보가 아직 확인되지 않았습니다. 지원 전 확인을 권장합니다.
- 근무지 출입구의 계단 없는 접근 가능 여부는 아직 확인되지 않았습니다. 지원 전 확인을 권장합니다.
- 저상버스 이용 가능 여부는 현재 데이터만으로 판단하기 어렵습니다. 지원 전 확인을 권장합니다.
- 주변 역 또는 출입구의 엘리베이터·리프트 정보가 충분하지 않습니다. 지원 전 확인을 권장합니다.

### 18.3 긍정 요인 문구 원칙

긍정 요인은 데이터에 근거해야 한다.

예시:

- 장애인 표준사업장으로 등록된 기업입니다.
- 장애인 전형 또는 우대 조건이 포함된 공고입니다.
- 공고 정보 기준으로 컴퓨터 사용 중심 업무에 가깝습니다.
- 공고 정보 기준으로 문서 작업 중심 업무에 가깝습니다.
- 공고 정보 기준으로 비교적 조용한 근무환경으로 분류됩니다.
- 현재 공공데이터 기준으로 근무지 주변 버스정류장 정보가 확인됩니다.
- 현재 공공데이터 기준으로 근무지 주변 지하철 접근성 정보가 확인됩니다.
- 현재 공공데이터 기준으로 근처 지하철역 또는 출입구의 엘리베이터 정보가 확인됩니다.
- 현재 공공데이터 기준으로 근처 휠체어 리프트 정보가 확인됩니다.

### 18.4 위험 요인 문구 원칙

위험 요인은 단정적 표현보다 확인 유도 표현을 우선한다.

나쁜 예시:

- 휠체어 사용자는 접근할 수 없습니다.
- 이 공고는 장애인에게 부적합합니다.
- 출근이 불가능합니다.

좋은 예시:

- 휠체어 이동에 필요한 역 엘리베이터 또는 리프트 정보가 충분하지 않습니다. 지원 전 확인을 권장합니다.
- 전화 응대 업무가 포함될 수 있어 사용자의 선호 조건과 다를 수 있습니다.
- 장시간 서기 또는 이동이 필요한 업무일 수 있어 확인이 필요합니다.
- 무거운 물건을 취급하는 업무가 포함될 수 있어 확인이 필요합니다.
- 장애인 표준사업장 여부는 현재 데이터에서 확인되지 않았습니다.
- 장애인 우대 또는 전형 여부는 현재 데이터에서 확인되지 않았습니다.

### 18.5 요약 문구 원칙

요약 문구는 짧고 안전하게 작성한다.

예시:

- 현재 데이터 기준 접근성 조건이 비교적 양호한 공고입니다.
- 현재 데이터 기준 접근성은 양호하지만, 일부 항목은 지원 전 확인이 필요합니다.
- 일부 접근성 항목은 확인이 필요하지만, 기본 조건은 검토 가능한 공고입니다.
- 현재 데이터만으로는 접근성 판단이 제한적입니다. 지원 전 주요 항목 확인이 필요합니다.

## 19. evidence_items 정책

`evidence_items`는 추천/설명 결과의 근거 데이터이다.

가능하면 다음 정보를 포함한다.

- source_type
- source_name
- record_id
- field_name
- field_value
- distance_meters
- description

공공데이터가 부족하거나 아직 연결되지 않은 경우에도 API가 실패해서는 안 된다.

이 경우 다음 방식으로 반환한다.

- `record_id`는 없을 수 있다.
- 설명에는 “현재 데이터 기준”, “확인 필요” 표현을 사용한다.
- 데이터가 없는 상황 자체를 시스템 오류로 처리하지 않는다.

## 20. 테스트 정책

현재 MVP 단계에서는 실제 공공데이터가 충분히 들어오지 않았을 수 있다.

따라서 테스트는 다음 방향으로 작성한다.

- 데이터가 없을 때 API가 실패하지 않아야 한다.
- 데이터가 없을 때 빈 배열 또는 확인 필요 문구를 반환해야 한다.
- 데이터가 없다는 이유만으로 테스트를 실패시키지 않는다.
- “접근 불가”가 아니라 “확인 필요” 정책이 적용되는지 검증한다.
- 설명 문구는 너무 자주 깨지지 않도록 핵심 포함 여부 중심으로 검증할 수 있다.

예시:

- `risk_factors`에 확인 필요 문구가 포함되는지 확인
- `positive_factors`가 비어 있을 경우 기본 안내 문구를 반환하는지 확인
- `evidence_items`가 없거나 record_id가 없어도 응답이 정상인지 확인
- `used_llm=false`, `explanation_version="v1-rule-fallback"`이 유지되는지 확인

## 23. 구현 시 주의사항

### 23.1 표현 주의

다음 표현은 피한다.

- 장애인에게 부적합합니다.
- 출근이 불가능합니다.
- 접근할 수 없습니다.
- 지원하지 않는 것이 좋습니다.
- 위험합니다.

다음 표현을 우선한다.

- 확인이 필요합니다.
- 현재 데이터 기준으로는 판단이 제한적입니다.
- 지원 전 확인을 권장합니다.
- 사용자의 선호 조건과 다를 수 있습니다.
- 일부 항목은 추가 확인이 필요합니다.

### 23.2 데이터 처리 주의

- 공공데이터가 비어 있어도 API가 실패하지 않아야 한다.
- PostGIS 조회 결과가 없어도 fallback이 동작해야 한다.
- record_id가 없어도 evidence_items 구조는 유지할 수 있어야 한다.
- 위경도 값이 잘못된 경우 안전하게 무시하거나 확인 필요로 처리한다.
- 데이터 부족을 장애 사용자에게 불리하게 단정하지 않는다.

### 23.3 UI/UX 주의

- 지도만 제공하지 말고 목록도 함께 제공한다.
- 색상만으로 상태를 표현하지 않는다.
- 필터는 단계별로 입력하게 한다.
- 민감 정보는 선택 입력으로 둔다.
- 사용자가 입력하지 않아도 기본 추천을 이용할 수 있게 한다.
- 어려운 용어에는 설명을 제공한다.

우선순위는 다음과 같다.

9. 운영 환경 배포 설정

DB/PostGIS 실데이터 연결 전까지는 테스트/계약/구조 안정화를 우선한다.

## 25. 에이전트 작업 원칙

BridgeWork 관련 작업을 수행하는 에이전트는 다음 원칙을 따른다.

1. 사용자의 장애 유형을 이유로 가능성을 단정하지 않는다.
2. 데이터가 없을 때는 “확인 필요”로 처리한다.
3. 점수 계산은 룰 기반으로 유지한다.
4. LLM은 설명 생성에만 사용한다.
5. API 응답에는 가능하면 근거 데이터를 포함한다.
6. 공공데이터가 비어 있어도 API가 실패하지 않게 한다.
7. 테스트는 실데이터 부재 상황을 고려한다.
