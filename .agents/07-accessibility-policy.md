# 07. Accessibility Policy

## 기본 원칙

BridgeWork는 장애인 구직자를 핵심 사용자로 하는 서비스이다.

따라서 FastAPI 응답도 프론트가 접근성 있는 화면을 만들 수 있도록 설계해야 한다.

UI는 Next.js가 담당하지만, FastAPI는 접근성 있는 설명과 상태값을 제공해야 한다.

## WCAG 2.2 AA 기준

서비스 전체는 WCAG 2.2 AA 준수를 목표로 한다.

FastAPI는 다음 정보를 응답에 포함하여 프론트 접근성을 지원한다.

- 점수 숫자
- 점수 라벨
- 점수 이유 텍스트
- 주의사항 텍스트
- 색상에 의존하지 않는 상태값
- 스크린리더용 짧은 요약
- 상세 설명
- unknown 또는 추가 확인 필요 항목

## 상태 라벨

색상만으로 상태를 구분하지 않도록 텍스트 라벨을 항상 제공한다.

권장 라벨은 다음과 같다.

- 접근 양호
- 일부 확인 필요
- 접근 주의
- 데이터 부족
- 추가 확인 필요

## 시각장애 또는 저시력 사용자 고려

응답에는 점수만 제공하지 말고 이유를 함께 제공한다.

예시는 다음과 같다.

- 접근성 점수 82점
- 주변 500m 이내 버스정류장 정보가 확인됩니다.
- 일부 횡단보도에 점자블록 정보가 있습니다.
- 음향신호기 정보는 확인되지 않아 추가 확인이 필요합니다.

프론트에서 목록형 대체 UI를 만들 수 있도록 지도 마커용 요약 정보도 제공한다.

## 휠체어 사용자 고려

휠체어 사용자에게 중요한 정보는 다음과 같다.

- 계단 없는 출입 가능성
- 엘리베이터 유무
- 휠체어 리프트 유무
- 보도턱낮춤 여부
- 장애인 화장실 여부
- 경사로 여부
- 자동문 여부
- 지하철 엘리베이터 출입구 위치
- 저상버스 접근 가능성

FastAPI는 확인 가능한 데이터와 확인 불가능한 데이터를 분리하여 반환한다.

## 청각장애 사용자 고려

청각장애 사용자에게 중요한 정보는 다음과 같다.

- 전화응대 여부
- 대면 커뮤니케이션 많음 여부
- 문자 또는 채팅 기반 커뮤니케이션 가능 여부
- 수어 통역 필요 여부
- 필담 가능 여부
- 면접 편의 제공 여부

확인되지 않은 업무환경은 단정하지 않는다.

## 인지 접근성 고려

AI 설명은 짧고 명확해야 한다.

원칙은 다음과 같다.

- 긴 문장 지양
- 어려운 용어는 쉽게 설명
- 항목별 요약 제공
- 좋은 점과 확인할 점 분리
- 오류 메시지는 구체적으로 작성

좋은 오류 메시지 예시는 다음과 같다.

- 희망 직무를 1개 이상 선택해주세요.
- 통근 범위를 선택해주세요.
- 사업장 좌표가 없어 접근성 분석을 할 수 없습니다.
- 현재 데이터로는 엘리베이터 유무를 확인할 수 없습니다.

나쁜 오류 메시지 예시는 다음과 같다.

- 입력 오류
- 실패
- 잘못된 요청
- 분석 불가

## 사용자 표시 문장 원칙

좋은 문장 예시는 다음과 같다.

- 이 공고는 희망 직무와 유사합니다.
- 주변 대중교통 정보가 확인됩니다.
- 휠체어 접근성은 일부 확인이 필요합니다.
- 시각장애 사용자에게 필요한 음향신호기 정보는 확인되지 않았습니다.
- 지원 전 회사에 전화응대 여부를 확인하는 것이 좋습니다.

피해야 할 문장 예시는 다음과 같다.

- 완벽히 접근 가능합니다.
- 장애인에게 최적입니다.
- 이 사용자는 지원하면 안 됩니다.
- 문제가 없습니다.
- 무조건 추천합니다.

## 민감정보 UX 원칙

장애 유형과 필요한 지원은 선택 입력이어야 한다.

사용자에게 안내할 때는 다음 흐름을 권장한다.

- 더 정확한 접근성 추천을 위해 장애 유형과 필요한 지원을 선택할 수 있어요.
- 입력하지 않아도 기본 일자리 추천은 이용할 수 있어요.

FastAPI는 장애 유형이 없는 요청도 처리해야 한다.

장애 유형이 없으면 일반 접근성 정보와 공고 적합도 중심으로 분석한다.
