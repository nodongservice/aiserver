# 접근성 점수 계산 정책 가이드

## 1. 목적

이 문서는 BridgeWork FastAPI AI/GIS Service의 접근성 점수 계산 기준을 정의한다.

접근성 점수는 사용자의 장애 유형, 필요 지원 조건, 이동 선호, 업무환경 선호/기피 조건, 공고 정보, 그리고 README.md에 정의된 공공데이터 동기화 대상 데이터만을 근거로 계산한다.

최종 점수는 룰 기반으로 계산한다.

LLM은 점수를 직접 계산하거나 변경하면 안 된다. LLM은 이미 계산된 점수, 긍정 요인, 위험 요인, 근거 데이터를 바탕으로 사용자 친화적 설명만 생성한다.

### 2.3 README에 없으므로 직접 사용하지 않는 데이터

아래 항목은 README.md의 동기화 대상에 없으므로 MVP 점수 계산에 직접 사용하지 않는다.

- 저상버스 운행 여부 또는 저상버스 노선별 차량 정보
- 별도 장애인 편의시설 표준데이터
- 경사도/고도 데이터
- 보행자전용도로 표준데이터
- 주차장/장애인전용주차구역 데이터
- 실시간 대중교통 도착 정보
- 실시간 시설 고장 정보
- 건물 내부 자동문/근무층/실내 경사로 상세 데이터

사용자가 이 항목을 필요 지원으로 선택하더라도, README 기준 동기화 데이터로 확인할 수 없으면 “확인 필요”로 표현한다.

## 3. 기본 원칙

### 3.1 점수는 룰 기반이다

FastAPI는 정해진 scoring rule에 따라 점수를 계산한다.

점수 계산에 사용하는 주요 데이터는 다음과 같다.

- 사용자 장애 유형
- 사용자 필요 지원 조건
- 사용자 업무환경 선호/기피 조건
- 사용자 이동수단 선호
- 공고의 업무환경 태그
- 공고의 지원 태그
- 장애인 표준사업장 여부
- 장애인 우대/전형 여부
- 근무지 주변 버스정류장
- 근무지 주변 횡단보도
- 근무지 주변 신호등
- 음향신호기
- 보행자작동신호기
- 보도턱낮춤
- 점자블록
- 지하철 출입구 리프트
- 휠체어 리프트
- 철도/역사 교통약자 편의시설
- 근로지원인 수행기관
- 교통약자 이동지원센터

### 3.2 데이터가 부족하면 단정하지 않는다

공공데이터에 정보가 없다고 해서 “접근 불가”로 단정하지 않는다.

데이터가 부족한 경우에는 다음 방식으로 처리한다.

- 점수는 과도하게 높이지 않는다.
- risk_factors에 “확인 필요” 문구를 추가한다.
- summary에 “일부 접근성 정보는 확인이 필요합니다.”를 반영할 수 있다.
- evidence_items에는 확인 가능한 근거만 담는다.

### 3.3 positive_factors와 risk_factors는 항상 함께 반환한다

추천 결과에는 긍정 요인과 위험 요인을 함께 제공한다.

사용자에게 좋은 점만 보여주면 안 된다. 특히 접근성 정보는 사용자의 실제 이동 가능성과 업무 적합성에 영향을 줄 수 있으므로 위험 요인을 숨기지 않는다.

### 3.4 장애 유형별 중요도는 다르게 본다

같은 시설이라도 장애 유형에 따라 중요도가 다르다.

예:

- 휠체어 사용자에게는 엘리베이터, 리프트, 보도턱낮춤, 계단 없는 접근 가능 여부가 중요하다.
- 시각장애 사용자에게는 음향신호기, 점자블록, 보행자작동신호기, 잔여시간표시기가 중요하다.
- 청각장애 사용자에게는 전화 업무 회피, 문자/필담 지원, 면접 편의 제공이 중요하다.
- 지체장애 사용자에게는 장시간 서기, 무거운 물건 들기, 긴 이동 동선이 위험 요인이 될 수 있다.

## 4. 총점 구조

최종 접근성 점수는 0~100점 범위를 사용한다.

| 항목 | 최대 점수 | 설명 |
|---|---:|---|
| transport_score | 20 | 버스정류장 중심 대중교통 접근성 |
| station_access_score | 20 | 지하철/역사/리프트 접근성 |
| crosswalk_score | 20 | 횡단보도/신호등/보행 안전 접근성 |
| facility_score | 20 | 표준사업장/역사 편의시설/지원 인프라 접근성 |
| work_environment_score | 20 | 업무환경 적합성 |
| risk_penalty | 음수 | 위험 요소 감점 |

총점 계산:

`total = transport_score + station_access_score + crosswalk_score + facility_score + work_environment_score + risk_penalty`

최종 점수는 0~100 범위로 보정한다.

## 5. 등급 기준

| 등급 | 점수 기준 | 의미 |
|---|---:|---|
| GOOD | 80점 이상 | 접근성 조건이 비교적 양호한 공고 |
| CAUTION | 60점 이상 80점 미만 | 일부 확인이 필요하지만 검토 가능한 공고 |
| RISK | 60점 미만 | 사용자 조건과 충돌하거나 접근성 정보가 부족한 공고 |

주의:

- GOOD이어도 risk_factors가 있을 수 있다.
- RISK라고 해서 지원 불가를 의미하지 않는다.
- RISK는 “지원 전 확인 필요성이 높음”을 의미한다.

## 7. 대중교통 접근성 점수

항목명: `transport_score`

최대 점수: `20점`

### 7.1 기본 기준

| 조건 | 점수 |
|---|---:|
| 반경 500m 이내 버스정류장 2개 이상 | +10 |
| 반경 500m 이내 버스정류장 1개 | +6 |
| 가장 가까운 버스정류장 300m 이내 | +5 |
| 가장 가까운 버스정류장 500m 이내 | +3 |
| 버스정류장 정보 없음 | +0 |

### 7.2 장애 유형별 보정

| 조건 | 점수 |
|---|---:|
| 이동약자 또는 휠체어 사용자 + 버스정류장 300m 이내 | +2 |
| 버스 선호 사용자 + 버스정류장 있음 | +2 |

### 7.3 확인 필요 조건

README 기준 데이터에는 저상버스 운행 여부 데이터가 없다.

따라서 다음 상황에서는 점수 가점이 아니라 risk_factors에 확인 필요 문구를 추가한다.

- 사용자가 저상버스 이용 가능 여부를 중요 조건으로 선택한 경우
- 버스정류장은 있으나 저상버스 운행 여부를 확인할 수 없는 경우
- 대중교통 정보가 전혀 없는 경우

권장 문구:

- “근무지 주변 버스정류장 정보는 확인되지만, 저상버스 운행 여부는 현재 데이터만으로 판단하기 어렵습니다.”
- “저상버스 이용 가능 여부는 지원 전 확인을 권장합니다.”

## 8. 지하철/역사 접근성 점수

항목명: `station_access_score`

최대 점수: `20점`

### 8.1 기본 기준

| 조건 | 점수 |
|---|---:|
| 지하철 출입구 리프트 정보 있음 | +8 |
| 휠체어 리프트 정보 있음 | +6 |
| 지하철/역사 접근성 시설이 300m 이내 | +4 |
| 지하철/역사 접근성 시설이 500m 이내 | +2 |
| 한국철도공사 교통약자 편의시설에서 휠체어리프트수 확인 | +3 |
| 한국철도공사 교통약자 편의시설에서 장애인경사로유무 확인 | +3 |
| 한국철도공사 교통약자 편의시설에서 장애인화장실유무 확인 | +2 |

### 8.2 휠체어 사용자 보정

| 조건 | 점수 |
|---|---:|
| 휠체어 사용자 + 지하철 출입구 리프트 있음 | +4 |
| 휠체어 사용자 + 휠체어 리프트 있음 | +3 |
| 휠체어 사용자 + 리프트/역사 편의시설 정보 없음 | risk_factors 추가 |

### 8.3 확인 필요 조건

다음 상황에서는 risk_factors에 확인 필요 문구를 추가한다.

- 휠체어 사용자에게 필요한 리프트 정보가 없는 경우
- 지하철 접근성 시설 데이터가 부족한 경우
- 역명 또는 출입구 좌표 매핑 신뢰도가 낮은 경우
- 역사 편의시설 정보가 역 단위로만 있어 실제 출입구 동선까지 확정하기 어려운 경우

주의:

- README 기준으로 “지하철 엘리베이터 전용 위치 데이터”는 별도 SourceType으로 명시되어 있지 않다.
- 따라서 엘리베이터라는 표현은 `SEOUL_SUBWAY_ENTRANCE_LIFT`, `SEOUL_TRANSPORT_WEAK_WHEELCHAIR_LIFT`, `KORAIL_WEEK_PERSON_FACILITIES`, `RAIL_WHEELCHAIR_LIFT`, `SEOUL_WHEELCHAIR_LIFT` 등에서 확인 가능한 리프트/교통약자 편의시설 정보 중심으로 사용한다.

## 9. 횡단보도/보행 안전 점수

항목명: `crosswalk_score`

최대 점수: `20점`

### 9.1 기본 기준

| 조건 | 점수 |
|---|---:|
| 반경 500m 이내 횡단보도 2개 이상 | +6 |
| 반경 500m 이내 횡단보도 1개 | +3 |
| 보행자신호등 있음 | +3 |
| 보행자작동신호기 있음 | +2 |
| 시각장애인용 음향신호기 있음 | +3 |
| 잔여시간표시기 있음 | +2 |
| 보도턱낮춤 있음 | +3 |
| 점자블록 있음 | +2 |

### 9.2 휠체어 사용자 보정

| 조건 | 점수 |
|---|---:|
| 휠체어 사용자 + 보도턱낮춤 있음 | +2 |
| 휠체어 사용자 + 보도턱낮춤 정보 없음 | risk_factors 추가 |
| 휠체어 사용자 + 횡단보도는 있으나 턱낮춤 없음 | risk_factors 추가 |

### 9.3 시각장애 사용자 보정

| 조건 | 점수 |
|---|---:|
| blind/low_vision + 음향신호기 있음 | +3 |
| blind/low_vision + 보행자작동신호기 있음 | +2 |
| blind/low_vision + 점자블록 있음 | +2 |
| blind/low_vision + 음향신호기 정보 없음 | risk_factors 추가 |
| blind/low_vision + 점자블록 정보 없음 | risk_factors 추가 |

### 9.4 확인 필요 조건

다음 상황에서는 risk_factors에 확인 필요 문구를 추가한다.

- 주변 횡단보도는 있으나 보행 안전 속성 정보가 없는 경우
- 음향신호기/점자블록/보도턱낮춤 여부가 확인되지 않는 경우
- 근무지 주변 보행 안전시설 정보가 부족한 경우

## 10. 사업장/편의시설 접근성 점수

항목명: `facility_score`

최대 점수: `20점`

### 10.1 기본 기준

| 조건 | 점수 |
|---|---:|
| 장애인 표준사업장으로 확인됨 | +8 |
| 장애인 우대/전형 공고로 확인됨 | +5 |
| 한국철도공사 교통약자 편의시설에서 장애인화장실 정보 확인 | +3 |
| 한국철도공사 교통약자 편의시설에서 장애인경사로 정보 확인 | +3 |
| 근로지원인 수행기관 정보가 근무지 생활권 내 확인됨 | +2 |
| 교통약자 이동지원센터 정보가 근무지 생활권 내 확인됨 | +2 |

### 10.2 휠체어 사용자 보정

| 조건 | 점수 |
|---|---:|
| 휠체어 사용자 + 역사 장애인화장실 정보 있음 | +2 |
| 휠체어 사용자 + 역사 장애인경사로 정보 있음 | +2 |
| 휠체어 사용자 + 표준사업장 확인 | +2 |

### 10.3 확인 필요 조건

다음 상황에서는 risk_factors에 확인 필요 문구를 추가한다.

- 사업장 건물 내부의 장애인 화장실 여부가 확인되지 않는 경우
- 사업장 출입구의 계단 없는 접근 가능 여부가 확인되지 않는 경우
- 표준사업장 여부가 확인되지 않는 경우
- 장애인 우대/전형 여부가 확인되지 않는 경우

주의:

- README 기준 동기화 대상에는 별도 “전국장애인편의시설표준데이터”가 없다.
- 따라서 사업장 건물 내부 장애인 화장실, 경사로, 자동문, 근무층 정보는 직접 점수 가점 근거로 사용하지 않고 확인 필요 항목으로 처리한다.
- KORAIL 교통약자 편의시설의 장애인화장실/경사로 정보는 역 단위 시설 정보로만 사용한다.

## 12. 위험 요소 감점

항목명: `risk_penalty`

risk_penalty는 음수 값으로 계산한다.

### 12.1 기본 감점

| 조건 | 감점 |
|---|---:|
| 필수 접근성 정보 다수 누락 | -5 |
| 사용자 기피 업무환경과 충돌 1개 | -5 |
| 사용자 기피 업무환경과 충돌 2개 이상 | -10 |
| 휠체어 사용자에게 리프트/역사 편의시설 정보 없음 | -5 |
| 사업장 내부 접근성 정보 확인 불가 | -3 |
| 공고 위치 좌표 없음 | -10 |
| GIS 근거 데이터 없음 | -5 |

### 12.2 감점 원칙

- 데이터 없음과 실제 불가능을 구분한다.
- 데이터 없음은 “확인 필요”로 표현한다.
- 사용자의 필수 지원 조건과 명확히 충돌할 때만 큰 감점을 준다.
- 중복 감점으로 점수가 과도하게 낮아지지 않도록 상한을 둔다.

권장 risk_penalty 하한: `-20`

## 13. 데이터 부족 정책

### 13.1 정보 없음

예:

- 사업장 내부 장애인 화장실 여부 데이터 없음
- 사업장 출입구 계단 없는 접근 여부 데이터 없음
- 저상버스 운행 여부 데이터 없음
- 실제 건물 내부 자동문/근무층 정보 없음

처리:

- risk_factors에 확인 필요 문구 추가
- 직접적인 불가능으로 표현하지 않음
- 점수는 보수적으로 계산

### 13.2 정보 일부 있음

예:

- 버스정류장 위치는 있으나 저상버스 여부 없음
- 횡단보도는 있으나 보도턱낮춤 정보 없음
- 역명은 있으나 출입구 좌표 없음
- 휠체어 리프트 위치는 있으나 실제 가동 상태가 불명확함

처리:

- 확인 가능한 부분만 positive_factors에 반영
- 부족한 부분은 risk_factors에 반영

### 13.3 정보 충돌

예:

- 사용자가 전화 업무를 피하고 싶은데 공고 태그에 phone_work가 있음
- 사용자가 장시간 서기 어려운데 long_standing_or_walking 태그가 있음
- 휠체어 사용자에게 접근성 시설 근거가 전혀 없음

처리:

- risk_factors에 명확히 표시
- risk_penalty 적용
- 등급이 GOOD이어도 summary에 확인 필요 반영

## 14. 장애 유형별 핵심 확인 항목

### 14.1 휠체어 사용자

핵심 확인 항목:

- 지하철 출입구 리프트
- 휠체어 리프트
- 보도턱낮춤
- 역사 장애인화장실/경사로 정보
- 사업장 출입구 계단 없는 접근 가능 여부
- 사업장 내부 장애인 화장실 여부
- 버스정류장 접근성
- 저상버스 운행 여부 확인 필요
- 장시간 서기/이동 업무 여부
- 무거운 물건 취급 여부

긍정 요인 예시:

- 현재 공공데이터 기준으로 근처 지하철 출입구 리프트 정보가 확인됩니다.
- 현재 공공데이터 기준으로 근처 휠체어 리프트 정보가 확인됩니다.
- 현재 공공데이터 기준으로 근무지 주변 횡단보도에 보도턱낮춤 정보가 확인됩니다.
- 장애인 표준사업장으로 등록된 기업입니다.

위험 요인 예시:

- 근무지 출입구의 계단 없는 접근 가능 여부는 아직 확인되지 않았습니다. 지원 전 확인을 권장합니다.
- 사업장 내부 장애인 화장실 정보는 현재 데이터에서 확인되지 않았습니다. 지원 전 확인을 권장합니다.
- 저상버스 이용 가능 여부는 현재 데이터만으로 판단하기 어렵습니다. 지원 전 확인을 권장합니다.

- 보행자작동신호기
- 점자블록
- 잔여시간표시기
- 복잡한 보행 동선 여부
- 화면 중심 업무 여부
- 안내/보조 지원 여부

긍정 요인 예시:

- 현재 공공데이터 기준으로 근무지 주변 시각장애인용 음향신호기 정보가 확인됩니다.

- 현재 공공데이터 기준으로 근무지 주변에 보행자작동신호기 정보가 확인됩니다.

위험 요인 예시:

- 근무지 주변 음향신호기 여부가 아직 확인되지 않았습니다. 지원 전 확인을 권장합니다.
- 근무지 주변 점자블록 여부가 아직 확인되지 않았습니다. 지원 전 확인을 권장합니다.

## 15. evidence_items 사용 원칙

각 evidence item은 다음 정보를 포함한다.

- source_type
- source_name
- description
- distance_meters
- record_id

### 15.1 record_id 기준

record_id는 기본적으로 Spring의 `public_data_record.id`를 사용한다.

이 값은 사용자가 “왜 이 점수인가요?”라고 물었을 때 원본 공공데이터를 추적하기 위한 기준이다.

### 15.2 evidence 생성 기준

다음 README 기반 데이터는 evidence_items로 남길 수 있다.

- `NATIONWIDE_BUS_STOP`: 근처 버스정류장
- `NATIONWIDE_CROSSWALK`: 근처 횡단보도, 보도턱낮춤, 점자블록
- `NATIONWIDE_TRAFFIC_LIGHT`: 근처 신호등, 보행자작동신호기, 음향신호기, 잔여시간표시기
- `SEOUL_SUBWAY_ENTRANCE_LIFT`: 지하철 출입구 리프트
- `SEOUL_TRANSPORT_WEAK_WHEELCHAIR_LIFT`: 서울교통공사 교통약자 휠체어리프트
- `RAIL_WHEELCHAIR_LIFT`: 국가철도공단 휠체어리프트 위치
- `RAIL_WHEELCHAIR_LIFT_MOVEMENT`: 휠체어리프트 이동동선
- `SEOUL_WHEELCHAIR_LIFT`: 서울교통공사 휠체어리프트 설치현황
- `KORAIL_WEEK_PERSON_FACILITIES`: 한국철도공사 교통약자 편의시설
- `KEPAD_STANDARD_WORKPLACE`: 장애인 표준사업장 근거
- `KEPAD_RECRUITMENT`: 장애인 구인 공고 및 업무환경 근거
- `KEPAD_SUPPORT_AGENCY`: 근로지원인 수행기관
- `TRANSPORT_SUPPORT_CENTER`: 교통약자 이동지원센터

### 15.3 evidence 개수 제한

권장 제한:

- source_type별 대표 1~3개
- 전체 evidence_items 10개 이하

## 16. LLM 사용 원칙

LLM은 점수 계산에 개입하지 않는다.

LLM 입력으로 사용할 수 있는 값:

- accessibility_score
- accessibility_grade
- score_detail
- positive_factors
- risk_factors
- evidence_items
- summary

LLM이 하면 안 되는 것:

- 점수 재계산
- 등급 변경
- 위험 요인 삭제
- 데이터 부족을 확정 표현으로 바꾸기
- 근거 없는 긍정 표현 추가

LLM 설명에서 반드시 유지해야 하는 표현 원칙:

- 데이터 부족은 “확인 필요”
- 위험 요인은 숨기지 않음
- 사용자의 장애 유형을 낙인찍는 표현 금지
- 지원 불가/불가능 같은 단정 표현 금지
- “지원 전 확인을 권장합니다” 형태의 안전한 표현 사용

## 17. 향후 개선 항목

### 17.1 scoring_version

현재 scoring rule 버전은 `v1.0`으로 고정한다.

`v1.0`의 의미:

- 총점 구조는 `transport_score + station_access_score + crosswalk_score + facility_score + work_environment_score + risk_penalty`
- 각 가산 항목 상한은 `20점`
- `risk_penalty` 하한은 `-20점`
- 등급 기준은 `GOOD >= 80`, `CAUTION >= 60`, `RISK < 60`
- README 기준 데이터 밖의 항목은 가점 근거가 아니라 `확인 필요` 또는 risk 요인으로 처리

사용 목적:

- 분석 결과 캐싱 키 고정
- 점수 정책 변경 추적
- 과거 분석 결과와 신규 분석 결과 구분

주의:

- 현재 API 응답 본문에는 `scoring_version` 필드를 추가하지 않는다.
- Spring은 캐시/저장 메타데이터에서 `v1.0`을 함께 관리하는 것을 권장한다.

### 17.2 feature importance 설명

향후 사용자가 “왜 이 공고가 추천됐나요?”라고 물었을 때 항목별 기여도를 설명할 수 있다.

예:

- 대중교통 접근성 +15
- 보행 안전 +12
- 업무환경 적합성 +18
- 위험 감점 -5

### 17.3 실제 경로 기반 분석

현재는 반경 기반 근접 검색이다.

향후 README 기준 데이터 중 `SEOUL_WALKING_NETWORK`를 활용해 다음을 고려할 수 있다.

- 실제 보행 링크 기반 거리
- 지하철 출입구별 접근 가능성
- 보행 네트워크 단절 여부
- 횡단보도/육교/교량/터널 포함 여부

README에 없는 경사도/고도, 실시간 시설 고장, 실시간 교통 정보는 별도 데이터 소스가 추가되기 전까지 점수 계산에 포함하지 않는다.

## 18. 현재 MVP 적용 범위

현재 MVP에서는 다음까지만 적용한다.

- 룰 기반 총점 계산
- 장애 유형별 일부 가중치
- PostGIS 기반 근접 시설 검색
- README 기준 공공데이터 SourceType 활용
- evidence_items.record_id 연결
- 데이터 부족 시 확인 필요 문구
- LLM은 설명 생성에서만 사용 예정

MVP에서는 다음은 제외한다.

- README에 없는 데이터 기반 점수 계산
- 저상버스 운행 여부 직접 판정
- 실제 보행 경로 탐색
- 실시간 교통 정보
- 시설 고장 여부
- 경사도/고도 분석
- 별도 장애인 편의시설 표준데이터 기반 사업장 내부 시설 판정
- LLM 기반 점수 계산
